# Use workflow-specific regional network batches

Product Availability polling and Store Catalog discovery have different request plans, failure semantics, and retry behavior, so a shared regional client would expose protocol mechanics to both workflows. Each workflow will instead depend on one batch operation: Product Availability receives ordered per-store success, failure, or skip outcomes, while Store Catalog Refresh receives ordered discovery observations plus scope-completeness metadata. These seams own the closed Market definitions, authentication once per batch, rate policy, regional endpoint adapters, and—in discovery—the circuit breaker. Expected request failures cross the boundary only as typed, retry-aware values containing the allowlisted fields `kind`, `retryable`, `status`, `code`, `type`, `service`, and a bounded generic `message`; URLs, headers, bodies, credentials, Axios objects, and raw causes remain private. Batch-wide auth or configuration failures and programming defects reject, per-store availability failures continue and update health, and partial Catalog Scope observations are persisted as incomplete before refresh rejection requests a retry.
