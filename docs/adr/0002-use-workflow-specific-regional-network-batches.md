# Use workflow-specific regional network batches

Product Availability polling and Store Catalog discovery have different request plans, failure semantics, and retry behavior, so a shared regional client would expose protocol mechanics to both workflows. Each workflow instead depends on one batch operation: Product Availability receives ordered per-store success, failure, or skip outcomes, while Store Catalog Refresh receives ordered discovery observations plus scope-completeness metadata.

These seams own the closed Market definitions, authentication once per batch, rate policy, regional endpoint adapters, and—in discovery—the circuit breaker. Product Availability accepts branded Market codes; only the Lambda transport adapter translates legacy Catalog Scope input. Store Catalog Refresh accepts branded Catalog Scopes and preserves Market identity separately.

Expected request failures cross the boundary only as typed, retry-aware values containing the allowlisted fields `kind`, `retryable`, `status`, `code`, `type`, `service`, and a bounded generic `message`; URLs, headers, bodies, credentials, Axios objects, and raw causes remain private. Batch-wide authentication transport failures reject as the same sanitized `NetworkFailureError` shape so retry metadata is retained. Configuration failures and programming defects reject normally, per-store availability failures continue and update health, and partial Catalog Scope observations are persisted as incomplete before refresh rejection requests a retry.
